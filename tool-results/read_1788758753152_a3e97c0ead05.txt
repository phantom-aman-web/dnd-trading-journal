     1→     1→# DnD — Build Worklog
     2→     2→
     3→     3→This file tracks the build of **DnD**, a private trading performance platform, following the
     4→     4→specification in `upload/DnD.md`. The spec defines 11 phases (Phase 0 through Phase 10).
     5→     5→
     6→     6→## Architectural Adaptations (per Spec Rule 4)
     7→     7→
     8→     8→The spec assumes Supabase/PostgreSQL + Supabase Auth + Supabase Storage. This sandbox provides
     9→     9→Prisma + SQLite and a local filesystem. Adaptations (documented honestly):
    10→    10→
    11→    11→1. **Database**: Prisma + SQLite. RLS is simulated via mandatory `userId` ownership checks in
    12→    12→   the service layer for every query (no client-side filtering as authorization).
    13→    13→2. **Currency amounts**: integer minor units (cents) stored as `BigInt`-compatible integers
    14→    14→   in SQLite `Integer` columns. Prices/quantities/ratios stored as `Text` decimal strings and
    15→    15→   processed through a pure decimal utility (no unsafe float math).
    16→    16→3. **Authentication**: credentials-based email + bcrypt password, signed httpOnly JWT session
    17→    17→   cookie. A demo user (`trader@dnd.local`) is pre-seeded so the app is usable immediately.
    18→    18→4. **Storage**: local filesystem under `/home/z/my-project/storage/` served through signed-URL
    19→    19→   API endpoints (short-lived token, ownership-validated).
    20→    20→5. **Routing**: per sandbox rule, the user-visible app lives entirely at `/` as a client-side
    21→    21→   SPA with view switching (Zustand). API routes live under `/api/*`.
    22→    22→6. **Tests**: per sandbox rule "do not write any test code," formal Vitest/Playwright suites
    23→    23→   are omitted. Correctness is enforced through strict TypeScript types, pure domain
    24→    24→   functions, and manual agent-browser verification of the golden path.
    25→    25→7. **Offline (Phase 8)**: lightweight version using `localStorage`-backed drafts + sync queue
    26→    26→   simulation. Full Dexie/IndexedDB sync engine deferred.
    27→    27→8. **Real-time**: not required for v1; no WebSocket mini-service.
    28→    28→9. **Phase coverage**: all 11 phases are implemented at functional depth. Phases 0-5 are full
    29→    29→   treatment; Phases 6-10 are solid MVPs.

   126→   126→Agent: main
   127→   127→Task: Fix page freeze when changing appearance/theme
   128→   128→
   129→   129→Work Log:
   130→   130→- Diagnosed root cause in src/components/theme-provider.tsx: the `ThemeSync` component set up a `MutationObserver` on `document.documentElement` watching attribute changes. When the user clicked a theme button, `setTheme()` wrote `data-theme` and toggled the `dark` class on `<html>`, which triggered the observer. The observer's callback then called `apply()`, which set the same attributes again, triggering the observer again — an infinite synchronous loop that froze the page completely.
   131→   131→- Fix: removed the `MutationObserver` entirely. The `setTheme()` function already writes directly to localStorage and the DOM, so no observer is needed. `ThemeSync` now only applies the stored theme once on mount (to survive SSR hydration) and otherwise stays out of the way.
