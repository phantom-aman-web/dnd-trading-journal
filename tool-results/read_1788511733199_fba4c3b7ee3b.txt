    63→    63→## Core positioning
    64→    64→
    65→    65→DnD connects:
    66→    66→
    67→    67→**Strategy → Trading Plan → Setup → Execution → Evidence → Result → Psychology → Review → Analytics → Improvement → Strategy**
    68→    68→
    69→    69→DnD exists to help a trader understand not only:
    70→    70→
    71→    71→**"Did I win?"**
    72→    72→
    73→    73→but:
    74→    74→
    75→    75→**"Why did I win or lose, did I follow my process, what evidence supports the decision, what behaviors are repeatedly hurting me, which strategy versions actually perform, and what should I change next?"**

    79→    79→# 2. PRODUCT NORTH STAR
    80→    80→
    81→    81→The product must make it possible for a trader to answer:
    82→    82→
    83→    83→> **How did I trade this week, why did I win or lose, and what should I change?**
    84→    84→
    85→    85→in approximately two minutes.
    86→    86→
    87→    87→The central learning loop is:
    88→    88→
    89→    89→```text
    90→    90→STRATEGY
    91→    91→   ↓
    92→    92→PLAN
    93→    93→   ↓
    94→    94→SETUP
    95→    95→   ↓
    96→    96→TRADE
    97→    97→   ↓
    98→    98→EVIDENCE
    99→    99→   ↓

   102→   102→PSYCHOLOGY
   103→   103→   ↓
   104→   104→REVIEW
   105→   105→   ↓
   106→   106→ANALYTICS
   107→   107→   ↓
   108→   108→IMPROVE
   109→   109→   ↓
   110→   110→STRATEGY VERSION
   111→   111→   ↺
   112→   112→```

   133→   133→

   135→   135→
   136→   136→- reasoning

   138→   138→- evidence
   139→   139→- psychology
   140→   140→- execution quality
   141→   141→- rules
   142→   142→- outcome
   143→   143→- lessons
   144→   144→
   145→   145→## 3.3 Understand performance
   146→   146→
   147→   147→The system should turn raw trade history into useful, evidence-based patterns.
   148→   148→
   149→   149→## 3.4 Protect sensitive data
   150→   150→

   173→   173→
   174→   174→# 4. IMPORTANT BUILDING AGENT RULES
   175→   175→
   176→   176→These rules are mandatory.
   177→   177→
   178→   178→1. Build in the defined phase order.
   179→   179→2. Do not silently expand scope.
   180→   180→3. Do not silently remove requirements.
   181→   181→4. If implementation requires a meaningful architectural deviation, explain it in the phase completion report.
   182→   182→5. Security requirements apply during every phase.
   183→   183→6. Financial calculations must be unit-tested before the related phase is considered complete.
   184→   184→7. Do not use frontend filtering as an authorization mechanism.
   185→   185→8. Do not trust client-calculated financial values.
   186→   186→9. Do not expose secrets to the client.
   187→   187→10. Do not mutate historical strategy versions.
   188→   188→11. Do not mutate original uploaded evidence when annotations are applied.
   189→   189→12. Do not silently overwrite conflicting offline/server changes.
   190→   190→13. Do not show NaN, Infinity, undefined or misleading zero values to users.
   191→   191→14. Do not create non-functional buttons.
   192→   192→15. Do not create fake loading states.
   193→   193→16. Do not create fake analytics.
   194→   194→17. Do not create fake AI functionality.
   195→   195→18. Do not block the main UI with heavy calculations.
   196→   196→19. Prefer maintainability over cleverness.
   197→   197→20. Prefer secure defaults.
   198→   198→21. Prefer explicitness over magic behavior.
   199→   199→

   206→   206→Each phase must result in a working application.
   207→   207→

   210→   210→- run type checking
   211→   211→- run linting
   212→   212→- run tests
   213→   213→- verify the relevant user flows
   214→   214→- verify security controls introduced in that phase
   215→   215→- verify responsive behavior
   216→   216→- summarize the implementation
   217→   217→- list anything intentionally deferred
   218→   218→- do not continue to the next phase until the phase is demonstrably stable
   219→   219→
   220→   220→The coding agent must not repeatedly rebuild the architecture from scratch.

   222→   222→Establish strong foundations first.

   318→   318→# 7. FINANCIAL DATA MODELING
   319→   319→
   320→   320→This is critical.
   321→   321→
   322→   322→Do not store all financial values as integer cents.
   323→   323→
   324→   324→Different types of financial values require different representations.
   325→   325→
   326→   326→## Currency amounts
   327→   327→
   328→   328→For fixed currency amounts, use integer minor units where appropriate.
   329→   329→
   330→   330→Example:
   331→   331→
   332→   332→USD 125.34
   333→   333→
   334→   334→stored as:
   335→   335→
   336→   336→12334 cents
   337→   337→
   338→   338→## Prices
   339→   339→
   340→   340→Use PostgreSQL `numeric` with an appropriate precision and scale.
   341→   341→
   342→   342→Examples:
   343→   343→
   344→   344→- entry price
   345→   345→- stop price
   346→   346→- target price
   347→   347→- exit price
   348→   348→
   349→   349→## Quantities
   350→   350→
   351→   351→Use exact decimal numeric representation.
   352→   352→
   353→   353→Examples:
   354→   354→
   355→   355→- lot size
   356→   356→- contracts
   357→   357→- shares
   358→   358→- position size
   359→   359→
   360→   360→## Ratios
   361→   361→
   362→   362→Use exact numeric representation.
   363→   363→
   364→   364→Examples:
   365→   365→
   366→   366→- risk percentage
   367→   367→- R multiple
   368→   368→- reward/risk
   369→   369→- win rate
   370→   370→
   371→   371→Do not perform money-critical arithmetic using unsafe JavaScript floating-point operations.
   372→   372→
   373→   373→Use deterministic decimal arithmetic.
   374→   374→
   375→   375→All server-side financial calculations must be validated.
