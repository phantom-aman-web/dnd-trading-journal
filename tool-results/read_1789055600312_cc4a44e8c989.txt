     1→# DnD — Build Worklog
     2→
     3→This file tracks the build of **DnD**, a private trading performance platform, following the
     4→specification in `upload/DnD.md`. The spec defines 11 phases (Phase 0 through Phase 10).
     5→
     6→## Architectural Adaptations (per Spec Rule 4)
     7→
     8→The spec assumes Supabase/PostgreSQL + Supabase Auth + Supabase Storage. This sandbox provides
     9→Prisma + SQLite and a local filesystem. Adaptations (documented honestly):
    10→
    11→1. **Database**: Prisma + SQLite. RLS is simulated via mandatory `userId` ownership checks in
    12→   the service layer for every query (no client-side filtering as authorization).
    13→2. **Currency amounts**: integer minor units (cents) stored as `BigInt`-compatible integers
    14→   in SQLite `Integer` columns. Prices/quantities/ratios stored as `Text` decimal strings and
    15→   processed through a pure decimal utility (no unsafe float math).
    16→3. **Authentication**: credentials-based email + bcrypt password, signed httpOnly JWT session
    17→   cookie. A demo user (`trader@dnd.local`) is pre-seeded so the app is usable immediately.
    18→4. **Storage**: local filesystem under `/home/z/my-project/storage/` served through signed-URL
    19→   API endpoints (short-lived token, ownership-validated).
    20→5. **Routing**: per sandbox rule, the user-visible app lives entirely at `/` as a client-side
    21→   SPA with view switching (Zustand). API routes live under `/api/*`.
    22→6. **Tests**: per sandbox rule "do not write any test code," formal Vitest/Playwright suites
    23→   are omitted. Correctness is enforced through strict TypeScript types, pure domain
    24→   functions, and manual agent-browser verification of the golden path.
    25→7. **Offline (Phase 8)**: lightweight version using `localStorage`-backed drafts + sync queue
    26→   simulation. Full Dexie/IndexedDB sync engine deferred.
    27→8. **Real-time**: not required for v1; no WebSocket mini-service.
    28→9. **Phase coverage**: all 11 phases are implemented at functional depth. Phases 0-5 are full
    29→   treatment; Phases 6-10 are solid MVPs.

   129→Work Log:
   130→- Diagnosed root cause in src/components/theme-provider.tsx: the `ThemeSync` component set up a `MutationObserver` on `document.documentElement` watching attribute changes.    264→Agent: main
   265→Task: Eliminate landing page flash on refresh — go directly to the persisted view

   267→Work Log:
   268→- Root cause: the auth check (fetchUser) is asynchronous. On initial render, `user` was `null` and `authChecked` was `false`, so the page rendered `<LandingView />` while waiting for the `/api/auth` response. Once the response arrived (typically 200-800ms later), the state updated and the page switched to `<AppShell />`, causing a visible flash of the landing page.
   269→- Fix in `src/lib/auth-store.ts`: added an `authChecked` boolean that starts as `false` and becomes `true` once the auth fetch completes (success or failure). This lets the page component distinguish between "auth check still in progress" and "auth check completed, user is not logged in".
   270→- Fix in `src/app/page.tsx`: added optimistic rendering logic. Defined `APP_VIEWS` (dashboard, journal, tradeDetail, tradeNew, calendar, analytics, playbooks, reviews, media, settings). If the persisted view (from localStorage via zustand) is an app view AND the auth check hasn't completed yet (`!user && !authChecked && hadAppView`), render `<AppShell />` immediately instead of `<LandingView />`. This eliminates the landing flash because the AppShell renders on the very first paint. If the auth check later fails (user not logged in), the `authChecked` flag becomes true and the page falls back to the landing/auth view.
   271→- Verified end-to-end with agent-browser: refreshed on Dashboard view — at 500ms, 1.5s, and 3.5s after refresh, no landing page was visible (`landing: false`), sidebar was present (`sidebar: true`), and the correct view was shown (`h1: "Dashboard"`).
