    53→# 1. PRODUCT IDENTITY

    55→## Product

    57→**DnD**

    59→## Category
    60→
    61→Private trading performance system.
    62→
    63→## Core positioning
    64→
    65→DnD connects:
    66→
    67→**Strategy → Trading Plan → Setup → Execution → Evidence → Result → Psychology → Review → Analytics → Improvement → Strategy**
    68→
    69→DnD exists to help a trader understand not only:
    70→
    71→**"Did I win?"**
    72→
    73→but:
    74→
    75→**"Why did I win or lose, did I follow my process, what evidence supports the decision, what behaviors are repeatedly hurting me, which strategy versions actually perform, and what should I change next?"**

    79→# 2. PRODUCT NORTH STAR
    80→
    81→The product must make it possible for a trader to answer:
    82→
    83→> **How did I trade this week, why did I win or lose, and what should I change?**
    84→
    85→in approximately two minutes.
    86→
    87→The central learning loop is:
    88→
    89→```text
    90→STRATEGY
    91→   ↓
    92→PLAN
    93→   ↓
    94→SETUP
    95→   ↓
    96→TRADE
    97→   ↓
    98→EVIDENCE
    99→   ↓
   100→RESULT
   101→   ↓
   102→PSYCHOLOGY
   103→   ↓
   104→REVIEW
   105→   ↓
   106→ANALYTICS
   107→   ↓
   108→IMPROVE
   109→   ↓
   110→STRATEGY VERSION
   111→   ↺
   112→```
   113→
   114→Every major feature must support this loop.
   115→
   116→Do not add features just because they are impressive.
   117→
   118→If a feature does not materially improve recording, understanding, reviewing, protecting, or improving trading performance, it should not be prioritized for the core product.

   174→# 4. IMPORTANT BUILDING AGENT RULES
   175→
   176→These rules are mandatory.
   177→
   178→1. Build in the defined phase order.
   179→2. Do not silently expand scope.
   180→3. Do not silently remove requirements.
   181→4. If implementation requires a meaningful architectural deviation, explain it in the phase completion report.
   182→5. Security requirements apply during every phase.
   183→6. Financial calculations must be unit-tested before the related phase is considered complete.
   184→7. Do not use frontend filtering as an authorization mechanism.
   185→8. Do not trust client-calculated financial values.
   186→9. Do not expose secrets to the client.
   187→10. Do not mutate historical strategy versions.
   188→11. Do not mutate original uploaded evidence when annotations are applied.
   189→12. Do not silently overwrite conflicting offline/server changes.
   190→13. Do not show NaN, Infinity, undefined or misleading zero values to users.
   191→14. Do not create non-functional buttons.
   192→15. Do not create fake loading states.
   193→16. Do not create fake analytics.
   194→17. Do not create fake AI functionality.
   195→18. Do not block the main UI with heavy calculations.
   196→19. Prefer maintainability over cleverness.
   197→20. Prefer secure defaults.
   198→21. Prefer explicitness over magic behavior.

   213→- verify the relevant user flows
   214→- verify security controls introduced in that phase
   215→- verify responsive behavior
   216→- summarize the implementation

   227→
   228→Use a modern production-oriented stack.
   229→
   230→Use the latest stable versions available at implementation time unless there is a documented reason not to.

   249→

   254→
   255→## Backend
   256→
   257→Use Next.js server-side capabilities, route handlers and server actions where appropriate.
   258→
   259→Keep business logic in dedicated service/domain layers rather than embedding it directly in presentation components.

   261→## Database

   266→Use:
   267→
   268→- foreign keys

   272→- typed database access
   273→
   274→## Authentication
   275→
   276→Prefer Supabase Auth or another mature authentication provider.
   277→
   278→Do not implement custom authentication unnecessarily.
   279→
   280→## Storage

   282→Use private object storage, preferably:
   283→

   318→# 7. FINANCIAL DATA MODELING
   319→
   320→This is critical.
   321→
   322→Do not store all financial values as integer cents.
   323→
   324→Different types of financial values require different representations.
   325→
   326→## Currency amounts
   327→
   328→For fixed currency amounts, use integer minor units where appropriate.
   329→
   330→Example:
   331→
   332→USD 125.34
   333→
   334→stored as:
   335→
   336→12334 cents
   337→
   338→## Prices
   339→
   340→Use PostgreSQL `numeric` with an appropriate precision and scale.
   341→
   342→Examples:
   343→
   344→- entry price
   345→- stop price
   346→- target price
   347→- exit price
   348→
   349→## Quantities
   350→
   351→Use exact decimal numeric representation.
   352→
   353→Examples:
   354→
   355→- lot size
   356→- contracts
   357→- shares
   358→- position size
   359→
   360→## Ratios
   361→
   362→Use exact numeric representation.
   363→
   364→Examples:
   365→
   366→- risk percentage
   367→- R multiple
   368→- reward/risk
   369→- win rate
   370→
   371→Do not perform money-critical arithmetic using unsafe JavaScript floating-point operations.
   372→
   373→Use deterministic decimal arithmetic.
   374→
   375→All server-side financial calculations must be validated.
